# Brainstorming: 테스트 인프라 잔여 항목 정리

## Details

### 항목 1 — 셰이더 등록 boilerplate 통합

`graphics_add_hlsl_shader()`가 이미 파일 경로에서 `_backend`를 자동으로 추론하므로(`get_filename_component`로 `renderer/<backend>/shaders/...`에서 뽑아냄), 각 호출마다 실제로 달라지는 값은 SOURCE 경로 / ENTRY_POINT / PROFILE 3개뿐이다.
11개 값들의 출력 변수(`_graphics_dx9_baseline_vs` 등)도 `GRAPHICS_SHADER_OUTPUTS`에 append하는 용도로만 쓰이고 다른 곳에서 개별 참조되지 않는다 — 즉 이름 있는 변수로 따로 붙잡아 둘 이유가 없다.

CMake는 네이티브 튜플이 없으므로, 한 줄에 `|` 같은 별도 구분자로 필드를 합친 문자열 리스트를 만들고 반복문 안에서 `string(REPLACE "|" ";" ...)` + `list(GET ...)`로 분해하는 방식을 제안한다.

```cmake
set(_graphics_shader_specs
    "renderer/directx9/shaders/Baseline.vs.hlsl|VSMain|vs_3_0"
    "renderer/directx9/shaders/Baseline.ps.hlsl|PSMain|ps_3_0"
    "renderer/directx11/shaders/Baseline.vs.hlsl|VSMain|vs_5_0"
    "renderer/directx11/shaders/Baseline.ps.hlsl|PSMain|ps_5_0"
    "renderer/directx12/shaders/Baseline.vs.hlsl|VSMain|vs_5_0"
    "renderer/directx12/shaders/Baseline.ps.hlsl|PSMain|ps_5_0"
    "renderer/directx9/shaders/Instancing.vs.hlsl|VSMain|vs_3_0"
    "renderer/directx11/shaders/Instancing.vs.hlsl|VSMain|vs_5_0"
    "renderer/directx12/shaders/Instancing.vs.hlsl|VSMain|vs_5_0"
    "renderer/directx11/shaders/Transform.cs.hlsl|CSMain|cs_5_0"
    "renderer/directx12/shaders/Transform.cs.hlsl|CSMain|cs_5_0"
)
foreach(_spec ${_graphics_shader_specs})
    string(REPLACE "|" ";" _spec_fields "${_spec}")
    list(GET _spec_fields 0 _rel_source)
    list(GET _spec_fields 1 _entry_point)
    list(GET _spec_fields 2 _profile)
    graphics_add_hlsl_shader(_shader_output "${CMAKE_SOURCE_DIR}/${_rel_source}" ${_entry_point} ${_profile})
    list(APPEND GRAPHICS_SHADER_OUTPUTS ${_shader_output})
endforeach()
```

새 셰이더 추가 시 데이터 목록에 한 줄만 넣으면 되고, 함수 호출부/append 로직은 반복문이 한 번만 처리한다.

### 항목 2 — `OpenGLRenderer` 테스트: 계획 수정 필요

**조사 결과** `OpenGLRenderer`는 실제 렌더러가 아니라 의도적인 스텁이다(`renderer/opengl/OpenGLRenderer.h` 주석: "OpenGL 실사용은 이번 범위에 포함되지 않는다").
- `Initialize()`: 인자 전부 무시, 항상 `true` 반환.
- `RenderFrame()`/`OnResize()`/`Shutdown()`: 완전히 빈 함수(no-op).
- `HandleUiMessage()`: 인자 전부 무시, 항상 `false` 반환.

즉 `DirectX9/11/12RendererTest`처럼 "실제 디바이스 초기화·리사이즈·렌더링이 성공하는지" 검증할 대상 자체가 없다 — 검증할 실제 동작이 없기 때문이다. 원래 리팩터 검사가 기대했던 "대등한 커버리지"는 이 클래스에는 적용할 수 없다.

대안 두 가지를 제안한다.

- **(A) 스텁 계약(contract) 테스트**: `Initialize()`가 `true`를 반환하는지, `HandleUiMessage()`가 `false`를 반환하는지, 나머지 호출들이 크래시 없이 도는지만 확인하는 아주 얇은 테스트를 추가한다. 지금 당장은 사소해 보이지만, 나중에 누군가 이 스텁을 실제 구현으로 바꾸기 시작할 때 "반환값 계약이 바뀌었다"는 걸 테스트가 알려주는 트립와이어 역할을 한다.
- **(B) 이번 사이클에서는 보류(Won't-fix)**: 스텁에 테스트를 추가하는 것 자체가 낮은 가치라고 보고, 리팩터 검사 항목을 "OpenGL은 의도적 스텁이라 DirectX와 대등한 커버리지 적용 대상이 아님"으로 재분류하고 닫는다. 실제 OpenGL 구현 착수 시점에 테스트를 새로 작성하는 게 더 합리적이라는 입장.

## Trade-offs

- **항목 1의 `|` 구분자 방식**: 가독성 있는 테이블 형태가 되지만, 셰이더 경로나 entry point에 실수로 `|` 문자가 들어가면 파싱이 깨진다 — 다만 HLSL 파일 경로/함수명에 `|`가 들어갈 일은 사실상 없어 실질적 위험은 낮다.
- **항목 2 (A) 안**: 테스트 코드가 하나 늘지만, 검증하는 내용이 "상수 반환값"뿐이라 버그를 잡아낼 실질적 힘은 약하다 — 그래도 리팩터 검사가 지적한 "커버리지 공백"은 문서상 해소된다.
- **항목 2 (B) 안**: 테스트는 늘지 않지만, 커밋 리포트에 다시 열린 이슈로 안 남기고 "이유 있는 종결"로 정리할 수 있다.
