# Brainstorming: WOT 요청 — IntroScene용 2D UI 위젯 렌더링 계약

## Details

- 계약 위치: 새 `ui/widgets/` 디렉토리에 `IUiBase.h`, `IUiElementRegistry.h`와 5종 구체 위젯, 기본 registry 구현을 둔다. 기존 `ui/directx{9,11,12}/ImGuiManagerDX{9,11,12}.cpp`(프레임 생명주기 전담)와는 폴더 자체를 분리해 책임을 섞지 않는다.
- `IUiBase`: `virtual void Render() = 0;`만 갖는 최소 계약. `virtual ~IUiBase() = default;`.
- `IUiElementRegistry`: `Add(IUiBase*)` / `Remove(IUiBase*)` / `RenderAll()`. non-owning으로 설계 — 포인터만 보관하고 위젯의 생성/소멸(수명)은 호출자(WOT)가 책임진다. 레지스트리 자체는 위젯의 구체 타입을 몰라도 되므로 SRP를 지킨다.
- 기본 구현체 `UiElementRegistry : IUiElementRegistry`도 함께 제공 제안 — `std::vector<IUiBase*>` 하나로 구현 가능하고 imgui 의존이 없어서, WOT이 매번 재구현하지 않아도 되고 graphics 쪽 단위 테스트로 계약 자체를 검증할 수 있다.
- `ButtonUI`/`ProgressUI`/`StringFieldUI`/`LabelUI`/`ImageUI`는 각각 `.cpp`에서 `imgui.h`를 직접 포함한다 — 요청 문서가 언급한 "imgui.h를 아는 파일 3개"가 이 5개 + registry 관련 파일만큼 늘어나는데, 이건 문제가 아니라 wrapper 계층이 의도적으로 확장되는 지점이다(다른 모듈은 여전히 imgui.h를 모른다).
- `ImageUI`의 텍스처 파라미터는 `ImTextureID`(ImGui가 자체 정의하는 opaque `void*`)로 받는다 — `IRenderer.h`의 "DirectX 전용 타입을 인터페이스에 노출하지 않는다" 원칙과 정합하고, DX9/11/12 백엔드마다 다른 텍스처 타입(`IDirect3DTexture9*`, `ID3D11ShaderResourceView*` 등) 문제를 자연스럽게 피한다.
- `IRenderer` 연결 지점: `virtual void SetUiElementRegistry(IUiElementRegistry* registry) = 0;` (요청 원문은 레퍼런스 예시였지만 포인터로 제안 — 아래 Trade-offs 참고). DX9/11/12 `RenderFrame` 내부, 기존 `m_uiManager->NewFrame()` 호출 이후 `m_uiManager->Render()` 호출 이전에 `if (m_uiElementRegistry) { m_uiElementRegistry->RenderAll(); }` 삽입. `OpenGLRenderer`는 멤버에 저장만 하고 실제 호출 배선은 하지 않는 no-op으로 구현.

## Trade-offs

- **레퍼런스 vs 포인터 시그니처**: 레퍼런스(`IUiElementRegistry&`)는 항상 유효한 대상을 요구해 "아직 registry가 없는 상태"를 표현할 수 없다 — WOT이 `IntroScene` 진입 전(예: `IRenderer::Initialize` 직후, Scene 전환 전) 시점에는 registry를 만들기 전일 수 있어 타이밍 문제가 생긴다. 포인터는 null 체크가 한 곳(`RenderFrame` 내부) 추가되는 대신 "미설정" 상태를 자연스럽게 표현한다.
- **기본 `UiElementRegistry` 구현 제공 여부**: 제공하면 WOT의 중복 구현을 막고 graphics 쪽에서 계약을 실제로 검증하는 단위 테스트를 붙일 수 있다. 미제공(인터페이스만)이면 WOT이 자유롭게 구현할 수 있지만, 실사용 예시 없이 인터페이스만 넘기는 셈이라 통합 시점에 문제가 드러날 위험이 커진다.
- **`ImageUI`의 Image vs ImageButton 분기 기준**: 요청 문서의 "텍스처 유무로 분기"라는 표현이 모호하다 — 문자 그대로 "텍스처가 있으면 그림, 없으면 다른 것"인지, 실제로는 "클릭 콜백이 있으면 `ImageButton`, 없으면 `Image`"를 의도한 것인지 불명확하다. 후자로 해석하는 게 UI 위젯 관례상 더 자연스럽지만, 임의로 단정하기보다 확인이 필요하다.

## Q&A Log

- Q1 (기본 구현체 `UiElementRegistry` 제공 여부): "기능이 추상화 되어있다면 구체적으로 projects와 종속성이 없다면 구현, 아니면 인터페이스만." → `UiElementRegistry`는 `std::vector<IUiBase*>`만으로 동작해 projects(WOT)의 어떤 구체 타입에도 의존하지 않으므로, **구현까지 제공**하기로 확정.
- Q2 (`SetUiElementRegistry` 포인터 vs 레퍼런스): "요청이 레퍼런스만 있다면 그거까지만." → 요청 원문이 레퍼런스로 명시돼 있으므로 **레퍼런스 시그니처를 그대로 따른다** (graphics가 임의로 포인터로 바꾸지 않는다). "미설정 상태" 문제는 각 렌더러 구현체 내부에서 포인터로 저장(초기값 `nullptr`)해 흡수하고, 공개 인터페이스 시그니처만 요청대로 레퍼런스 유지.
- Q3 (`ImageUI` Image vs ImageButton 분기 기준): "WOT에 되묻기." → 사용자(WOT 의도 확인 대상)에게 재질문한 결과 **"클릭 콜백 유무"**로 확정 — `onClick` 콜백이 주어지면 `ImGui::ImageButton`, 없으면 `ImGui::Image`.
- Q4 (위젯 생성자 파라미터): "graphics가 합리적으로 정하기, 필요하면 WOT에서 요청 올 것." → graphics가 최소 사용 가능한 형태로 정하고, 부족하면 WOT이 별도 요청을 보내는 것으로 확정.

## Summary & Open Questions (사용자 결정 필요)

**현재까지 확정한 방향**

- `ui/widgets/`에 `IUiBase`/`IUiElementRegistry` 인터페이스 + 5종 위젯 wrapper 신설.
- `IUiElementRegistry`는 non-owning 레지스트리로 설계, **기본 구현체 `UiElementRegistry`도 함께 제공** (projects 종속성 없음 → Q1 확정).
- `ImageUI`는 `ImTextureID`(opaque)를 받아 DirectX 구체 타입을 노출하지 않으며, `onClick` 콜백 유무로 `ImGui::ImageButton`/`ImGui::Image`를 분기한다 (Q3 확정).
- `IRenderer::SetUiElementRegistry`는 요청 원문대로 **레퍼런스** 시그니처 유지, 내부 저장은 포인터로 흡수 (Q2 확정).
- 위젯 생성자 파라미터는 graphics가 합리적으로 정한다 — 부족하면 WOT이 후속 요청을 보낸다 (Q4 확정).
- 이번 사이클 스코프는 추상 계약(인터페이스 + wrapper)까지이며, WOT이 상속할 구체 위젯(`IntroStartButton` 등)은 대상이 아니다.
