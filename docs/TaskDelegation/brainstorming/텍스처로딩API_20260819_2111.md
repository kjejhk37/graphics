# Brainstorming: WOT 요청 — ImageUI용 텍스처 로딩 공개 API

## Details

- **이미지 디코딩**: 새 서드파티 라이브러리(예: stb_image) 대신 **WIC(Windows Imaging Component, `<wincodec.h>` + `windowscodecs.lib`)**를 제안한다. Windows SDK에 포함된 OS 컴포넌트라 `fxc.exe`/`d3d9.lib`처럼 FetchContent 없이 시스템 링크만으로 쓸 수 있고, PNG/JPG/BMP를 전부 지원한다. 이 프로젝트가 이미 Windows 전용(HWND 기반)이라 이식성 손해도 없다. 이 선택지를 쓰면 `agent_harness/CLAUDE.md`의 Dependency Evaluation(`dependency_eval.md`) 절차 자체를 안 밟아도 된다 — WIC는 "새 외부 라이브러리 도입"이 아니라 이미 이 프로젝트가 쓰는 "Windows SDK 시스템 컴포넌트 사용" 패턴의 연장이기 때문이다.
- **내부 wrapper**: WIC 호출부는 `platform` 또는 `graphics` 안에 `WicImageLoader`류 내부 클래스로 감싸 파일 경로 → `(width, height, RGBA8 픽셀 버퍼)`만 반환하게 한다 - 그 뒤 DX9/11/12별 텍스처 생성은 각자 백엔드가 담당(기존 "외부 라이브러리는 wrapper로 감싼다" 원칙 그대로 적용).
- **DX9**: `D3DX9` 유틸리티가 현재 Windows SDK에 없으므로 `IDirect3DDevice9::CreateTexture` + `LockRect`/`UnlockRect`로 디코딩된 RGBA 픽셀을 직접 업로드한다. 반환 핸들은 `IDirect3DTexture9*`를 `void*`로 캐스팅 — ImGui DX9 백엔드가 그대로 `ImTextureID`로 받아들인다(추가 변환 불필요).
- **DX11**: `CreateTexture2D`(`D3D11_USAGE_DEFAULT`) + `CreateShaderResourceView`. 반환 핸들은 `ID3D11ShaderResourceView*`를 `void*`로 캐스팅 — DX9와 동일하게 ImGui DX11 백엔드가 그대로 받아들인다.
- **DX12**: 가장 복잡하다. `ImGuiManagerDX12`가 이미 갖고 있는 SRV 디스크립터 힙은 **폰트 전용 1슬롯 고정**이고, 그 파일 안 주석이 "여러 텍스처가 필요해지면 진짜 풀 할당자로 바꿔야 한다"고 이미 예고해뒀다. 두 방향이 있다.
  1. `ImGuiManagerDX12`의 힙을 확장하고 `AllocateSrvDescriptor`/`FreeSrvDescriptor`를 진짜 할당자로 교체.
  2. `DirectX12Renderer`가 **별도의 SRV 힙**을 새로 만들어 사용자 텍스처 전용으로 쓰고, `ImGuiManagerDX12`(폰트 전용)는 건드리지 않는다.

  (2)를 제안한다 — `ImGuiManagerDX12`의 책임(ImGui 프레임워크 자체 배선)과 `DirectX12Renderer`의 책임(이 요청이 추가하는 사용자 텍스처 관리)을 분리하는 게 SRP에 맞고, 기존 파일 수정 범위도 최소화된다. 반환 핸들은 `D3D12_GPU_DESCRIPTOR_HANDLE.ptr`(`UINT64`)을 `void*`로 재해석(캐스팅)한 값 — x64에서는 크기가 같아 안전하다.
- **인터페이스 위치**: `SetUiElementRegistry`와 같은 전례를 따라 `IRenderer`에 `LoadTexture`/`UnloadTexture`를 추가하는 걸 제안한다(이미 `HandleUiMessage`/`SetUiElementRegistry`로 UI 관련 메서드가 있는 인터페이스).
- **실패 처리**: 예외 대신 `nullptr` 반환 — 이 코드베이스 전반의 관례(`Initialize`가 `bool` 반환 등, 예외를 쓰지 않음)와 일치한다.
- **Unload**: 대칭성과 리소스 관리 원칙상 `UnloadTexture(void* handle)`도 함께 추가한다(요청 문서도 "필요하다고 판단되면 추가해도 된다"고 명시).

## Trade-offs

- **WIC vs stb_image**: WIC는 의존성 평가 절차를 생략할 수 있고 시스템 컴포넌트라 라이선스/유지보수 리스크가 없다는 장점이 크다. 단점은 API가 COM 기반이라 stb_image의 "함수 하나 호출"보다 코드가 길어진다는 것뿐 — 그 정도는 `WicImageLoader` wrapper 안에 다 갇힌다. 이 프로젝트 성격(Windows 전용, 시스템 SDK 컴포넌트를 이미 적극 사용)에는 WIC가 더 잘 맞는다고 판단.
- **DX12 힙 분리(제안 2번) vs 확장(1번)**: 분리하면 `ImGuiManagerDX12`를 안 건드려도 되지만 디스크립터 힙 관리 코드가 두 곳(폰트용/사용자 텍스처용)으로 나뉜다. 확장하면 힙은 하나지만 `ImGuiManagerDX12`의 책임 경계가 "ImGui 프레임워크"에서 "ImGui + 사용자 텍스처"로 넓어진다. SRP를 우선해 분리를 제안.
- **UnloadTexture 포함 여부**: 이번 사이클(`IntroScene`)은 텍스처 하나를 앱 종료까지 들고 있어 당장 필수는 아니지만, 나중에 Scene 전환이 잦아지면 텍스처를 안 풀어주는 API는 메모리 누수로 이어진다. 지금 만들어두는 비용이 낮아 포함을 제안.

## Q&A Log

- Q2 (DX9/11/12 전부 구현 vs 실사용 백엔드만): "실제로 쓰는 백엔드만 우선해줘." → WOT `src/projects/config/AppConfig.h`/`LaunchConfigStore.cpp` 확인 결과 기본(및 유일하게 실사용되는) 백엔드는 **DirectX11**. DX11만 실제 구현하고, DX9/DX12는 `OpenGLRenderer`와 동일하게 스텁(`LoadTexture`가 항상 `nullptr` 반환)으로 남긴다 — WOT이 실제로 DX9/DX12를 쓰게 되면 그때 새 요청으로 확장.
