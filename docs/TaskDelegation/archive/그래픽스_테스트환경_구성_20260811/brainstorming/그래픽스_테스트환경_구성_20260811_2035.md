# Brainstorming: 그래픽스 단위 테스트 환경 구성

## Details

1. **빌드 파이프라인 구성**
   `graphics/CMakeLists.txt`를 새로 작성한다. World-of-Tank-imitation-Refactoring(이하 projects)의 `CMakeLists.txt`에 있는 `platform_lib`/`graphics_lib` 관련 부분(FetchContent 5종: `nlohmann_json`, `tinyobjloader`, `ufbx`, `cgltf`, `imgui` + 소스 파일 목록 + include/link 설정)을 옮겨오되, platform 소스 경로는 하드코딩하지 않고 CMake 캐시 변수 `GRAPHICS_PLATFORM_DIR`(기본값 `${CMAKE_SOURCE_DIR}/../platform`)로 참조한다.

2. **platform 저장소는 건드리지 않는다**
   현재 세션 구성상 graphics/platform/projects가 각각 별도 Claude 세션이 담당하는 구조로 보인다. platform 저장소에 새 `CMakeLists.txt`를 추가하는 편이 더 깔끔할 수 있지만, 이는 platform 담당 세션의 영역이라 이번 작업 범위에서는 제외한다. 대신 graphics 쪽 `CMakeLists.txt`가 platform의 소스 파일을 직접 나열해 `platform_lib`를 구성하는 방식으로 우회한다.

3. **테스트 이전 범위 — 전체 이전, 1단계 → 2단계 순차 진행** (사용자 결정: 전체 이전 + 순차 진행, Q&A Log Q1/Q4 참조)
   projects의 `docs/archive/src구조재편_20260806/`에 이미 "Phase B에서 platform/graphics 테스트를 각자 저장소로 옮긴다"는 방향이 기록되어 있어, 이번 작업이 그 후속이라고 이해했다. 이전 대상 테스트 파일들을 확인해보니 필요 인프라 수준이 갈려서, 전략 문서의 구현 체크리스트는 아래 순서로 나눈다 — 사용자는 2단계까지 이번 사이클에 끝내는 것을 선호하지만, 2단계가 실제로 과도하게 버거우면 그 항목만 다음 사이클로 넘긴다.

   - **1단계 (먼저 진행)**: 디바이스/셰이더 자산 없이 도는 순수 로직 테스트.
     - `RendererBackendParserTest` — 순수 enum 파싱, 의존성 없음.
     - `RendererFactoryTest` — 팩토리로 객체 생성 후 `dynamic_cast`만 확인, `Initialize()` 호출 없음(실제 D3D 디바이스 불필요).
   - **2단계 (1단계 완료 후 이어서 진행)**: `ShaderBytecodeLoaderTest`, `DirectX9/11/12RendererTest`, `ImGuiManagerDX9/11/12Test`, `DirectX11/12ComputeDemoTest`.
     - 이 테스트들은 실제 WARP/D3D 디바이스 초기화(`Initialize()`)와 컴파일된 `.cso` 셰이더 파일을 요구한다.
     - 이걸 지원하려면 projects `CMakeLists.txt`의 `wot_add_hlsl_shader()` 커스텀 함수(`fxc.exe` 오프라인 셰이더 컴파일 파이프라인, 약 60줄)까지 통째로 이식해야 해서 1단계보다 범위가 크다 — 전략 문서에서 세부 하위 체크리스트로 쪼갠다.

4. **graphics 루트 `CLAUDE.md` 신설**
   projects의 `CLAUDE.md` 패턴을 따라 `@agent_harness/CLAUDE.md`를 import하는 최소 문서를 추가한다 — 지금 이 문서(`docs/`)를 쓰는 워크플로우 자체가 graphics 저장소에는 아직 문서화되어 있지 않다.

## Trade-offs

- **소스 파일 목록 중복**: `graphics/CMakeLists.txt`가 `platform_lib`/`graphics_lib`의 소스 파일 목록을 projects의 `CMakeLists.txt`와 별도로 유지하게 된다 — 파일이 추가/삭제될 때 두 곳을 동기화해야 하는 부담이 생긴다. (완화책: 두 파일 상단에 "이 목록은 상대 저장소의 CMakeLists.txt와 동기화 필요"라는 주석을 남긴다.)
- **FetchContent 중복**: `nlohmann_json`/`tinyobjloader`/`ufbx`/`cgltf`/`imgui` 5종을 graphics에서도 다시 선언해야 한다 — 빌드 캐시가 공유되지 않아 빌드 시간이 늘고, 버전이 projects와 어긋날 위험이 있다. (완화책: 버전 문자열을 동일하게 맞추고 출처를 주석으로 명시.)
- **1단계로 범위를 좁히면** "그래픽스 단위 테스트"라 부르기엔 커버리지가 얕다 — 렌더러 핵심 동작(`Initialize`/`RenderFrame`)이 빠진다. 하지만 셰이더 파이프라인까지 포함하면 이번 사이클이 projects `CMakeLists.txt`의 절반 가까이를 그대로 복제하는 수준으로 커진다.
- **platform 저장소를 안 건드리는 선택**은 세션 역할 분리를 지키지만, graphics 쪽 `CMakeLists.txt`가 platform 내부 폴더/파일 구조를 알아야 하는 형태가 된다 — platform이 자체 `CMakeLists.txt`를 갖는 편이 장기적으로는 더 깔끔하다.
