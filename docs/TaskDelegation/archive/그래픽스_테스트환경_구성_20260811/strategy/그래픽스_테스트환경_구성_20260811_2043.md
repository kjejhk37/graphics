# Strategy: 그래픽스 단위 테스트 환경 구성

## 확정된 방향 (브레인스토밍 결과 요약)

- 테스트 범위: **전체 이전** — 1단계(순수 로직) + 2단계(셰이더/디바이스) 모두 포함하되, 체크리스트를 1단계 → 2단계 순서로 나눠 순차 진행한다. 2단계가 실제로 과도하게 버거우면 그 항목만 `[DEFERRED]`로 표시하고 다음 사이클로 넘긴다.
- 이전 방식: **복사만** — projects(`World-of-Tank-imitation-Refactoring`)의 `tests/`, `CMakeLists.txt`는 이번 사이클에서 건드리지 않는다.
- 소스 목록 중복 완화책: **동기화 주석**만 남긴다 (별도 스크립트/도구 없음).
- platform 저장소 자체는 수정하지 않는다.

## How — 코드에 적용하는 방법

### 1. include 경로 해석 (조사 결과)

graphics/platform 두 저장소 모두 자기 자신을 가리키는 접두어로 include한다.
예: `graphics/renderer/RendererFactory.cpp` 안에서 `#include "graphics/renderer/RendererFactory.h"`,
`platform/math/Matrix4x4.cpp` 안에서도 마찬가지로 `platform/...` 접두어를 쓴다.
projects에서는 이게 `target_include_directories(..., PUBLIC src)`로 해결된다 — graphics/platform이 `src/graphics`, `src/platform`으로 서브모듈 배치되기 때문이다.

graphics 저장소 단독 빌드에서는 저장소 자신의 부모 폴더를 include 루트로 잡아야 이 접두어 규칙이 그대로 성립한다.
현재 실제 배치(`Claude/graphics`, `Claude/platform`)에서는 두 저장소가 형제 폴더이므로, 아래 두 include 디렉터리를 모두 추가한다.

```cmake
target_include_directories(graphics_lib PUBLIC
    ${CMAKE_SOURCE_DIR}/..            # "graphics/..." include를 위한 루트
    ${GRAPHICS_PLATFORM_DIR}/..       # "platform/..." include를 위한 루트
)
```

- `GRAPHICS_PLATFORM_DIR` 캐시 변수 기본값이 `${CMAKE_SOURCE_DIR}/../platform`이므로, 기본 배치에서는 두 경로가 실질적으로 같은 폴더(`Claude/`)로 수렴한다. 위치가 바뀌어도(`GRAPHICS_PLATFORM_DIR`를 다른 값으로 오버라이드해도) 규칙이 깨지지 않도록 두 항목을 각각 명시한다.

### 2. platform_lib / graphics_lib 소스 목록

- `platform_lib`: projects `CMakeLists.txt`의 `src/platform/` 접두어를 `${GRAPHICS_PLATFORM_DIR}/`로 바꿔서 그대로 나열 (`ufbx.c` 포함).
- `graphics_lib`: projects `CMakeLists.txt`의 `src/graphics/` 접두어를 `${CMAKE_SOURCE_DIR}/`로 바꿔서 그대로 나열 (imgui 소스/backends 포함).
- 두 목록 상단에 다음 주석을 남긴다 (Q&A A3 완화책).
  `// 이 목록은 World-of-Tank-imitation-Refactoring/CMakeLists.txt와 동기화 필요 — 파일 추가/삭제 시 두 곳을 함께 갱신할 것.`

### 3. 셰이더 파이프라인 (2단계)

- `wot_add_hlsl_shader()` 함수를 projects `CMakeLists.txt`에서 그대로 이식한다 (fxc.exe 탐색 로직 포함).
- projects는 `main` 실행 파일 기준으로 출력 디렉터리를 잡지만, graphics 저장소에는 `main`이 없다 — `tests` 타겟만 있으므로 출력 디렉터리는 처음부터 `${CMAKE_BINARY_DIR}/$<CONFIG>/shaders/<backend>`로 잡고(원본과 동일한 방식, 특정 타겟을 참조하지 않으므로 그대로 재사용 가능) `tests`에만 `add_dependencies`한다.
- 대상 셰이더 11개는 이미 `graphics/renderer/<backend>/shaders/*.hlsl`에 실존 확인됨 — 새로 옮길 필요 없음.

### 4. cube.obj 픽스처

- `DirectX9/11/12Renderer::Initialize()`가 내부적으로 상대 경로 `assets/models/cube.obj`를 읽는다 (조사 확인됨).
- `World-of-Tank-imitation-Refactoring/tests/fixtures/model_import/cube.obj`를 `graphics/tests/fixtures/model_import/cube.obj`로 **복사**한다.
- `tests` 타겟에 `POST_BUILD` 커스텀 커맨드로 `$<TARGET_FILE_DIR:tests>/assets/models/cube.obj`에 복사한다 (projects와 동일 패턴, `main` 쪽 복사는 생략 — graphics에 `main`이 없음).

### 5. 테스트 파일 복사 대상 (8개, projects `tests/` 원본 유지)

`ShaderBytecodeLoaderTest.cpp`, `DirectX9RendererTest.cpp`, `DirectX11RendererTest.cpp`, `DirectX12RendererTest.cpp`, `ImGuiManagerDX9Test.cpp`, `ImGuiManagerDX11Test.cpp`, `ImGuiManagerDX12Test.cpp`, `DirectX11ComputeDemoTest.cpp`, `DirectX12ComputeDemoTest.cpp`
(1단계 2개 `RendererBackendParserTest.cpp`, `RendererFactoryTest.cpp`는 별도 항목)

모두 `graphics/...`, `platform/...` 헤더만 참조 — 수정 없이 그대로 복사 가능 (조사 확인됨).

## 최종 승인 및 검증 기준

- Phase 0~2(1단계)는 필수 완료 조건 — `cmake --build` 성공 + `ctest`로 `RendererBackendParserTest`/`RendererFactoryTest` 통과.
- Phase 3~4(2단계)는 사용자가 이번 사이클에 포함을 선호하나, 진행 중 범위가 과도하게 커지면 해당 Phase를 `[DEFERRED]`로 표시하고 커밋 리포트에 사유를 남긴 뒤 다음 사이클로 넘긴다 — 이 경우 즉시 작업을 멈추고 사용자에게 알린 뒤 진행 여부를 재확인한다 (agent_harness 원칙).
- Phase 5는 규모가 작아 Phase 0~4와 병행 또는 마지막에 처리.
